# Product Roadmap: ChatGPT-Supervised Local Worker

The target product is a hybrid agent system:

- ChatGPT Web is the control plane. It interprets the user's goal, plans work, delegates tasks, reviews results, and makes semantic approval decisions.
- A local orchestrator owns durable task state. It continues running when a ChatGPT response ends or the Secure MCP Tunnel disconnects.
- Claude Code is a replaceable worker adapter. It may use DeepSeek, GLM, Qwen, or another configured model to read code, edit files, and run bounded commands.
- MCP is a short-lived control API, not the lifetime of a worker process.
- Notifications wake the user when attention is required. The MCP server does not assume it can wake a stopped ChatGPT conversation.

The existing synchronous harness remains the policy-gated low-level runner and development fallback. It is not the final product control plane.

## Product Invariants

1. A submitted task receives a stable task ID and is persisted before execution starts.
2. Tunnel, Bridge, browser, or orchestrator restarts cannot silently turn an unfinished task into success.
3. Retried MCP requests use idempotency keys and cannot accidentally duplicate a write task.
4. `blocked_on` is represented as an actionable waiting state, not success or a generic crash.
5. Approval decisions are bound to one task, one exact action fingerprint, one task revision, and an expiry time.
6. Local hard policy always has final authority. GPT approval cannot authorize secret access, project-root escape, dangerous deletion, destructive Git operations, or approval bypass.
7. Terminal and attention-required events are written to a notification outbox and retried without duplicating notifications.
8. Worker output is evidence. Completion still requires the configured validation gate.

## Target Components

### ChatGPT MCP adapter

Expose stable control tools and keep each request short:

- `worker_submit`
- `worker_get`
- `worker_list`
- `worker_get_events`
- `worker_get_result`
- `worker_cancel`
- `worker_resume`
- `approval_list`
- `approval_get`
- `approval_decide`
- `worker_capabilities`

The current `cc_plan_task`, `cc_review_task`, and `cc_run_approved_task` tools remain compatibility and diagnostic calls. They may later become submit-and-bounded-wait wrappers.

### Local orchestrator

Use SQLite with WAL mode as the authoritative state store. Keep JSONL only as an audit/export surface.

Minimum task states:

```text
queued -> starting -> running -> validating -> completed
                         |             |
                         +-> waiting_approval
                         +-> waiting_input
                         +-> stalled
                         +-> recovering
                         +-> failed / cancelled / expired
```

The orchestrator owns task leases, heartbeats, attempts, checkpoints, event ordering, approval records, and notification delivery.

### Worker adapters

The first adapter invokes Claude Code through the existing harness. Provider and model selection stay outside the MCP tool schema so DeepSeek, GLM, Qwen, and future backends can be changed without republishing the ChatGPT app schema.

Prefer structured worker events and a resumable session identifier when the installed Claude Code version supports them. If a runtime approval cannot be safely resumed in-process, persist a checkpoint, stop the worker, and resume through a new bounded invocation after approval.

### Notification adapters

Start with a local Windows notification and one optional remote channel such as PushPlus, email, or a generic webhook. Notifications contain a task ID, state, and redacted summary; they do not contain secrets or full local paths.

## Approval Record

An approval is a persisted object, not caller-supplied audit text. At minimum it contains:

```json
{
  "approval_id": "stable-id",
  "task_id": "stable-id",
  "task_revision": 3,
  "action_fingerprint": "sha256-of-canonical-action",
  "tool": "Write",
  "arguments_redacted": {},
  "risk_class": "workspace_write",
  "status": "pending",
  "expires_at": "ISO-8601 timestamp",
  "decision": null
}
```

Approval updates use an atomic compare-and-swap rule. Expired, superseded, already-decided, or fingerprint-mismatched approvals are rejected.

## Delivery Phases

### Phase A: releasable synchronous Alpha

- Mock harness, Doctor, protocol smoke, and documentation hygiene pass.
- Real plan and real write protocol smokes have independent switches.
- `blocked_on` has a regression test and cannot be reported as success.
- Repository packaging excludes secrets, local configuration, backups, run artifacts, and local paths.
- README clearly labels the synchronous and trusted-code limitations.

### Phase B: durable asynchronous core

- SQLite schema and migrations.
- Background orchestrator entrypoint.
- Submit, get, list, cancel, events, and result APIs.
- Idempotent submission, task leases, heartbeat, restart recovery, and process-tree cleanup.
- Notification outbox with a local notifier.

### Phase C: runtime approval and resume

- First-class `waiting_approval` and `waiting_input` states.
- Action fingerprints, expiry, one-shot decisions, and local hard-policy enforcement.
- Claude Code adapter checkpoint/resume experiment and documented fallback behavior.
- End-to-end test covering request, notification, decision, resume, and final validation.

### Phase D: Secure MCP Tunnel and ChatGPT Web

- Create and refresh the ChatGPT Developer mode app against the stable tool schema.
- Verify submit returns before the worker finishes.
- Verify work continues through a Tunnel disconnect and is readable after reconnect.
- Verify completion and approval notifications wake the user, who can return to the original conversation and recover state by task ID.
- Verify a real bounded workspace write followed by GPT review.

### Phase E: optional protocol capabilities

Expose MCP Tasks, elicitation, or progress notifications only after ChatGPT capability negotiation proves support. Internal durable task semantics must not depend on experimental client behavior.

## Non-Goals

- No untrusted-code execution without an OS isolation layer.
- No broad shell or arbitrary filesystem MCP tool.
- No assumption that GPT can override local hard policy.
- No assumption that MCP can wake a stopped ChatGPT conversation.
- No dependency on Codex CLI as the normal user entrypoint.
